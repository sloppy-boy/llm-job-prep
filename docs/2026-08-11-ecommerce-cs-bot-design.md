# 电商售后智能客服系统 — 设计文档

- **日期**：2026-08-11
- **作者**：小邋遢（求职作品集项目）
- **状态**：已评审，进入实施计划阶段
- **项目目标**：面向**大模型应用开发岗位**的求职作品集，演示 RAG + 多 Agent 协作 + 工具调用 + 商用级工程化能力

---

## 1. 项目定位

> 一个带**工具调用**的电商售后智能客服：用户问订单/物流/退换货问题时，系统不仅能基于知识库准确回答，还能**实际查订单、查物流、发起退款申请**，并带审核机制的多 Agent 协作。

**核心差异化**（区别于纯文档问答 demo）：机器人能"办事"不只是"说话"——查数据、做动作、可转人工。

**目标用户**：示例电商平台的消费者。

---

## 2. 用户场景与交互

### 2.1 用户可见功能

| 功能 | 说明 |
|------|------|
| 自然语言问答 | 问售后政策、商品问题、订单问题 |
| **工具调用** | 查订单状态、查物流轨迹、发起退款申请 |
| 多轮对话 | 记得上下文，可追问 |
| 流式回答 | SSE 逐字显示 |
| 引用溯源 | 答案下方附知识库来源 |
| 智能兜底 | 文档外/闲聊问题明确告知，不瞎编 |
| 转人工 | 多次解决不了时转人工（标记会话） |

### 2.2 页面形态（商用客服工作台，三栏）

采用商用"客服工作台"三栏布局（形态 3）：
- **左栏**：会话列表（多会话、新建会话）
- **中栏**：聊天窗口（消息列表 + 结构化卡片 + 输入框 + 猜你想问快捷入口 + 满意度评价）
- **右栏**：上下文面板（RAG 知识命中实时展示 + 状态指示）

**结构化卡片**由后端 SSE 事件驱动，把工具调用结果可视化：
- 订单卡片（状态/商品/金额）· 物流卡片（轨迹）· 退款卡片（申请单号/状态）

SSE 事件序列：`thinking`（正在识别）→ `card`*（工具结果卡片）→ `token`*（流式文本）→ `sources`（知识命中）→ `done`。

### 2.3 典型交互

```
用户：我的订单 20260811001 现在到哪了？
  → 路由判定：订单问题
  → 检索 Agent：知识库找物流说明
  → 工具：query_logistics("20260811001") → 返回"已发货，运输中"
  → 写作 Agent：组织回答
  → 审核 Agent：通过
  → 流式输出 + 来源

用户：那我还能申请退款吗？
  → 多轮记忆：关联上文订单
  → 检索政策 + 工具 request_refund（模拟写入）
  → 输出结果
```

## 4. 组件详细设计

### 4.1 前端（Next.js + TypeScript）

- 单页聊天界面：消息列表、输入框、SSE 流式渲染、引用来源卡片
- **范围锁定**：不做登录、多页面、复杂状态管理
- 通过 `fetch` + `ReadableStream` 消费 FastAPI 的 SSE

### 4.2 FastAPI 应用层

- `POST /api/v1/chat`：接收 `{ session_id, message }`，返回 SSE 流
- `GET /api/v1/health`：健康检查
- `GET /api/v1/metrics`：暴露延迟 / token / 成本统计
- 中间件：请求 ID、结构化日志、速率限制、CORS、API Key 校验
- 统一错误格式（RFC 风格 `{ error: { code, message } }`）
- 配置管理：`pydantic-settings` + `.env`（dev/prod 分离）

### 4.3 LangGraph 多 Agent 编排（核心）

**状态（State）**：`session_id, question, history, domain, retrieved_chunks, draft_answer, review_result, iteration_count, tool_results`

**节点与条件边**：

```
[路由 router] ──非文档问题──→ [直接回答] → 结束
      │ 文档/工具问题
      ▼
[检索 retriever] → 调 RAG 工具（混合检索+重排）
      ▼
[执行工具 tool_executor] → 查订单/物流/退款（按需）
      ▼
[写作 writer] → 基于检索内容+工具结果组织回答
      ▼
[审核 reviewer] → 检查：忠于检索？遗漏要点？幻觉？
      │  不合格且 iteration < 2
      ▼ 打回 writer（带审核反馈）
      │  合格 或 超限
      ▼
[输出] → 结束
```

**循环控制**：审核打回最多 2 次；超限输出当前版本并标记"未经最终审核"。

### 4.4 工具层（mock 业务系统）

| 工具 | 签名 | 行为 |
|------|------|------|
| `query_order` | (order_id) → 订单状态/明细 | 查 mock SQLite `orders` 表 |
| `query_logistics` | (order_id) → 物流轨迹 | 查 mock `logistics` 表 |
| `request_refund` | (order_id, reason) → 申请单号 | 写入 mock `refunds` 表 |
| `escalate_to_human` | (session_id) → 标记 | 会话置"转人工"状态 |

参数由 LLM 通过 Function Calling 结构化抽取，输出过 pydantic 校验。

### 4.5 RAG 模块（独立 Python 模块，不依赖 LangGraph）

- **分块**：递归字符分块 + 按标题切分；策略对比实验（记录准确率差异）
- **Embedding**：`BAAI/bge-m3`（SiliconFlow API）
- **混合检索**：向量检索 + BM25 关键词检索，加权融合
- **Rerank**：`BAAI/bge-reranker-v2-m3`（SiliconFlow API）精排 Top-3~5
- **向量库**：Qdrant（Docker），repository 接口抽象（可切换 Chroma 等）

### 4.6 语料构建（自建示例电商知识库）

- 20-40 篇 Markdown，目录结构：
  ```
  knowledge_base/
  ├── policies/   售后政策：退货/退款/换货/7天无理由/保修
  ├── logistics/  物流：发货时效/运费/丢件/快递查询
  ├── products/   商品知识：分类说明/规格/常见FAQ
  └── misc/       账号/支付/隐私/用户协议
  ```
- 风格建模自真实电商平台公开政策（可参考淘宝/京东/拼多多公开售后规则改写）
- **故意埋"硬骨头"**：含大表格（运费表）、嵌套条款（退款分情形）、长条款——制造分块与检索优化空间，形成面试素材

### 4.7 数据层

- **mock 订单库**：SQLite，表 `orders / logistics / refunds`，预置多条不同状态的示例订单
- **会话历史**：PostgreSQL 表 `sessions / messages`
- **语义缓存**：Redis（问题向量 hash 命中，降级用进程内存）

## 5. 数据流（一次问答）

```
页面输入 → Next.js → FastAPI /api/v1/chat
  → LangGraph 启动：[路由] 判定域
  → [检索] 调 RAG：bge-m3 向量化问题 → Qdrant 混合检索 → bge-reranker 精排
  → [工具执行] 按需调用 query_order / query_logistics / request_refund
  → [写作] 基于检索+工具结果生成
  → [审核] 校验，不合格打回（≤2次）
  → FastAPI 以 SSE 流式返回 → Next.js 逐字渲染
  → 记录会话到 Postgres，更新成本指标
```

## 6. 错误处理矩阵

| 故障 | 策略 |
|------|------|
| 主模型超时/失败 | 指数退避重试 3 次 → 降级备用模型 |
| 检索为空 | 明确告知"知识库无相关内容"→ 可转人工，不瞎编 |
| 订单号查不到 | 引导确认 → 失败则转人工 |
| 审核不通过 | 打回重写，上限 2 次，超限输出并标记 |
| 流式中断 | 客户端断开即取消生成 |
| 异常输入 | pydantic 校验 + 长度限制 + 基础敏感词过滤 |
| 刷接口 | API Key + 每会话限流 |

## 7. 评测方案

- **数据集**：25 个测试问题，5 类（订单/政策/商品/闲聊/边界刁钻题），每题标注期望要点
- **打分**：LLM-as-judge（独立模型），四维：正确性 / 忠于检索 / 完整性 / 是否幻觉 + 人工抽查
- **产出**：
  - 基线 vs 优化后准确率对比报告（面试的"提升 X%"）
  - badcase 清单与修复记录
