# 评测集扩充设计（25 → ~78 题）

> 日期：2026-08-18 · 项目：llm-job-prep（电商售后智能客服）
> 背景：简历使用评测数字前，用户担心 25 题样本量太小、100% 说服力不足。本设计将评测集扩充至约 78 题并重跑真实评测，拿到更扎实、经得起追问的数字。

## 一、现状

- 评测集 `backend/eval/questions.json`：25 题，5 类（order 5 / policy 5 / product 5 / chitchat 5 / edge 5）
- 评测方式：`python -m eval.judge` → 每题走 `run_agent` 真实链路 → LLM-as-judge 按 `expected_points` 判 PASS/FAIL
- 真实评测需：DeepSeek / SiliconFlow Key（`.env` 已就绪）、后端停止（Qdrant 本地模式独占锁）
- 现有基线：25/25 = 100%（2026-08-14，judge 稳定性修复后）

## 二、目标

- 评测集扩到 **78 题**，拆 6 类（order 10 / logistics 6 / policy 22 / product 18 / chitchat 8 / edge 14，合计 78）
- 全部题目**必须能被系统实际回答**（知识库内容 + mock 订单/物流库），不考"系统根本没数据的题"
- 保留原 25 题为基线（方便对照：25 题基线 vs 78 题全量），**原题不改**（除必要的 expected_points 校正）
- 重跑真实评测，输出诚实数字（可能低于 100%，正是扩充的意义）

## 三、数据改动

### 3.1 mock 订单/物流（`backend/app/tools/mock_db.py`）

- 订单 4 → 10：保留现有 4 个订单（ID `20260811001`–`20260811004`）**不动**，新增 6 个覆盖更多状态（待付款 / 待发货 / 已发货 / 运输中 / 已签收 / 退款中 / 已完成 / 已取消）
- 物流记录：给多数订单补齐（含已有 2 条）；保留 1-2 个"订单存在但无物流记录"的用例
- 兼容性：`_init_db` 的 `INSERT OR IGNORE` 天然兼容新增行；不改既有 schema
- 所有订单归属 `user-001`（DEMO_USER），沿用现有越权校验路径

### 3.2 知识库（`backend/knowledge_base/`）

沿用现有 frontmatter 格式（`title` / `category` / `order` / `status`），新增文档均 `status: published`（非 draft，可被检索）：

- **policy 新增**（支撑 policy 类 20 题）：
  - 运费险（理赔规则、抵扣方式）
  - 质量问题退换货（15 天 / 运费卖家承担）
  - 价格保护（价保期、补差方式）
  - 优惠券 / 红包 / 云豆使用与退回规则
  - 会员等级与权益（积分、专属客服、免运费等）
  - 客服渠道与工作时间（在线 / 电话 / 转人工）
  - 发票说明（普通 / 专票，与 FAQ Q2 对齐）
  - 订单取消 / 未按约定时间发货赔付（5% 上限 30 元）
- **product 新增**（支撑 product 类 16 题）：
  - 智能手表 SKU（规格 / 续航 / 防水 / 表带）
  - 扫地机器人 SKU（吸力 / 导航 / 自动集尘）
  - 厨房电器 SKU（电饭煲 / 破壁机等）
  - FAQ 扩充（新条目：赠品 / 保价 / 假一赔三 / 正品保障等）
- 新增后需 **reindex**（`POST /api/v1/kb/reindex` 或等价路径）再跑评测，否则检索不到新内容
- 内容风格与现有文档一致：电商售后话术、表格化事实、无虚构

### 3.3 评测集（`backend/eval/questions.json`）

- 保留原 25 题，新增 53 题（78 - 25 = 53）
- 题目编写原则：
  - 直接事实题（可从单篇文档查证）
  - 多点覆盖题（`expected_points` 列 2-4 个要点，如"退款到账时间按支付方式不同"）
  - 负面 / 边界题（订单不存在、越权查别人订单、空输入、域外话题）
  - 每题的 `expected_points` 与知识库 / mock 数据**逐条可溯源**（附来源标注，便于复盘）
- 新增 `logistics` 类：查物流工具调用 + 运费 / 配送时效政策

## 四、运行与坏例处理

1. 停后端（Qdrant 独占锁）
2. 起后端 → `POST /api/v1/kb/reindex`（全量重建，跳 draft）→ 停后端
   （reindex 走 `kb.reindex()`：读全部 md → chunk → 写 qdrant_local → 刷新 BM25；须在无其他进程持锁时执行）
3. `cd backend && .venv/Scripts/python -m eval.judge` 跑全量（加载已持久化的索引）
4. 坏例分级处理：
   - **知识库真缺** → 补文档 / 完善该题，保证"题目可答"前提下重测
   - **模型答错（有数据没答对）** → 记录 badcase，可能触发系统改进（RAG / 路由 / 工具调用）
   - **judge 误判** → 修 judge 稳定性（沿用"推理先行 + 最后一行裁决"）
   - **expected_points 表述歧义** → 校正题目（记录修正理由）
5. 输出：六类准确率 + 总准确率 + badcase 清单（含失败原因归类）

## 五、交付物

1. 扩充后的评测集 + mock 数据 + 知识库文档
2. 真实评测结果（诚实数字，含坏例归类）
3. 更新 `README.md` 与 `CONTEXT.md` 的评测数字（当前 100% → 新数字；注明题量）
4. 面试叙事更新：评测集 25→78 题、六类场景覆盖
5. 简历数字采用新评测结果（回到简历流程，重新定智能客服项目写法）

## 六、范围外（不做）

- 不改产品功能代码（除非坏例暴露真实 bug）
- 不扩 Docker / CI 评测 job（维持现状，本地跑）
- 不合并 feature 分支到 main（GitHub Flow 分支操作按用户后续指示）
